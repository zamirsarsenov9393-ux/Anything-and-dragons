# A&D — конструктор персонажей для D&D 5e. Архитектура (этап 1)

Версия документа: 0.3, 19.11.2026. Статус: на утверждении.

Изменения в 0.3: название A&D, публикация на GitHub Pages.

Изменения в 0.2: отдельный продукт (не клубный билдер), два языка (русский и английский), варианты публикации.

Рядом лежат три файла кода, которые уже проверены компилятором:

- `src/db/schema.ts` — схема SQLite на Drizzle (17 таблиц, миграция `drizzle/0000_init.sql` применяется без ошибок);
- `src/content/schema.ts` — формат контент-пакета на Zod (корректный пакет проходит, битый даёт 12 понятных ошибок);
- `src/core/types.ts` — типы движка правил: журнал решений, лист персонажа, интерфейс редакции.

## 1. Разбор ТЗ

### Что в ТЗ главное

Три вещи определяют всю архитектуру:

1. **Персонаж любого уровня и повышение уровня — один механизм.** Если хранить готовый лист, то создание на 15-м уровне, отмена повышения и восстановление версии превращаются в три разных кода с тремя наборами ошибок. Поэтому персонаж хранится как журнал решений по уровням, а лист каждый раз вычисляется заново.
2. **Контент отделён от кода.** Классы, заклинания и предметы — это данные в пакетах. Движок знает только правила редакции: как считать модификатор, бонус мастерства, ячейки при мультиклассе.
3. **Происхождение каждого элемента.** У любой записи есть источник, лицензия и список разрешённых действий. Отключение источника не ломает персонажей.

### Противоречия и пробелы в ТЗ

| Место в ТЗ | Проблема | Предлагаемое решение |
|---|---|---|
| SQLite и IndexedDB одновременно | Две базы для одних данных — рассинхрон | SQLite — единственная база. IndexedDB — запасное хранилище, если браузер не даёт OPFS, и место для бинарных файлов (портреты, резервные копии) |
| Импорт документов | Извлечение текста из PDF книг почти всегда упирается в права | В первой версии импорт только JSON-пакетов. Импорт документов — этап 9, только незащищённые файлы и только после заявления о правах |
| Тексты SRD | SRD 5.1 и 5.2.1 опубликованы на английском | Два языка на выбор (раздел 6). Русский перевод SRD — отдельный пакет: CC-BY-4.0 разрешает переработку с указанием авторства и пометкой об изменениях |
| PWA на iPhone | Safari удаляет данные сайта, который не открывали 7 дней, если он не добавлен на экран «Домой» | Просить установку на экран «Домой», вызывать `navigator.storage.persist()`, напоминать о резервной копии |
| Нет сервера | Публиковать как-то всё равно нужно | Статический хостинг (вопрос в конце) |

### Отношение к билдеру «Что угодно и драконы»

Это отдельный продукт со своим названием и стилем из ТЗ (графит, чёрный, приглушённое золото, тёмно-коричневый, пергамент). Клубный билдер остаётся как есть. Из него берутся только проверенные идеи: персонаж как план по уровням, разбор «откуда это число», метка источника на каждом элементе, набор расчётных тестов. Клубный контент сюда не переносится; если понадобится, его можно подключить обычным пакетом.

## 2. Архитектура

### Слои

```
┌─────────────────────────────────────────────────────────┐
│ app/  React + Tailwind + shadcn/ui                      │
│   features/: builder, sheet, level-up, spells,          │
│   inventory, campaigns, library, settings               │
├─────────────────────────────────────────────────────────┤
│ services/  сценарии: createCharacter, levelUp,          │
│   importPackage, exportPdf, backup  (связывают слои)    │
├──────────────────────────┬──────────────────────────────┤
│ core/  ЧИСТЫЙ TypeScript │ content/                      │
│  rules-engine            │  схема пакета (Zod)           │
│  editions/2014, /2024    │  загрузчик, проверка, граф    │
│  level-engine            │  зависимостей, резолвер,      │
│  multiclass              │  лицензии                     │
│  spells, inventory       │                               │
│  formula (парсер)        │                               │
├──────────────────────────┴──────────────────────────────┤
│ data/  Drizzle-схема, миграции, репозитории             │
├─────────────────────────────────────────────────────────┤
│ workers/db.worker.ts  SQLite WASM + OPFS                │
│ запасной путь: SQLite в памяти + снимок в IndexedDB     │
└─────────────────────────────────────────────────────────┘
```

Правило зависимостей: стрелки идут только вниз. `core/` не импортирует React, Drizzle и браузерные API — поэтому весь движок тестируется в Node за миллисекунды. Границы проверяет ESLint (`eslint-plugin-boundaries`), сборка падает при нарушении.

### Стек и почему так

| Задача | Выбор | Причина |
|---|---|---|
| Сборка | Vite + TypeScript strict | Быстро, PWA-плагин из коробки |
| UI | React 19, Tailwind 4, shadcn/ui, Motion для анимаций | По ТЗ; компоненты shadcn копируются в проект и перекрашиваются под стиль |
| База | `@sqlite.org/sqlite-wasm`, VFS `opfs-sahpool` | Работает без заголовков COOP/COEP — значит, подходит любой статический хостинг. Поддерживается в Safari 17+ |
| ORM | Drizzle, драйвер `sqlite-proxy` | Запросы уходят в воркер сообщениями, основной поток не блокируется |
| Валидация | Zod 4 | Одна схема и для импорта пакетов, и для типов |
| Состояние UI | Zustand для черновика мастера, TanStack Query поверх репозиториев | Черновик мастера не пишется в базу на каждое нажатие |
| PDF | pdf-lib + встроенный кириллический шрифт | Работает офлайн, без внешних CDN |
| Тесты | Vitest, fast-check, Playwright (движок WebKit — как Safari на iPhone) | См. раздел 7 |
| PWA | vite-plugin-pwa (Workbox) | Офлайн-кэш оболочки и контент-пакетов |

### Хранение на устройстве

1. При запуске воркер открывает SQLite в OPFS. Если OPFS недоступен (старый браузер, встроенный браузер Instagram или Telegram), база открывается в памяти, а её снимок сохраняется в IndexedDB через 2 секунды после каждого изменения.
2. Если недоступно и это, приложение работает в памяти и показывает предупреждение: данные пропадут после закрытия.
3. Перед каждой миграцией схемы делается резервная копия (`backup_record.kind = 'pre-migration'`).
4. Облачная синхронизация потом добавляется отдельным слоем: у всех записей ULID и `updated_at`, ревизии персонажей неизменяемы — это готовая основа для слияния без конфликтов.

## 3. Схема базы данных

Полный код — `src/db/schema.ts`. Здесь — смысл.

### Связи

```
content_source 1──* content_package 1──* content_item 1──* content_item_text (ru / en)
                                    1──* content_dependency (from_uid → to_uid)

campaign 1──* character 1──* character_revision 1──* character_content_ref
campaign *──* player (через campaign_player)
campaign 1──* adventure_log
character 1──1 character_state
character 1──* inventory_item ──? content_item (по uid, мягкая ссылка)
character / campaign 1──* note
```

### Библиотека контента

- **content_source** — книга или документ: название, издатель, редакция, версия документа, код лицензии, текст атрибуции, основание прав, `allowed_use` (хранить механику / хранить текст / показывать текст / экспортировать текст / делиться). Флаг `enabled` отключает источник целиком.
- **content_package** — версия пакета: с контентом или с переводом. Первичный ключ `(id, version)`: старые версии остаются в базе, пока на них ссылаются персонажи. Активна одна.
- **content_item** — элемент конкретной версии пакета. `mechanics` — данные для движка, общие для всех языков.
- **content_item_text** — название и описание элемента на каждом языке. Строки приходят из пакета с контентом или из пакета-перевода. Если лицензия не разрешает хранить текст, остаётся только название. Для частых фильтров заклинаний (круг, школа, концентрация, ритуал) вынесены отдельные колонки с индексами. `hash` — sha-256 канонического JSON механики.
- **content_dependency** — граф: подкласс → класс, способность → класс и уровень, заклинание → список заклинаний класса, магический предмет → базовый предмет.
- **content_fts** — виртуальная таблица FTS5 для поиска по названию, тегам и краткому описанию. Создаётся отдельной SQL-миграцией.

### Персонажи

- **character** — карточка: имя, кампания, игрок, редакция, статус (черновик, активен, на пенсии, погиб, пропал), биография, указатель `current_revision_id`.
- **character_revision** — неизменяемая версия журнала решений (`build`). Каждое создание, повышение, правка, импорт или восстановление добавляет новую ревизию со ссылкой на родителя. `summary` — кэш для списков (уровень, классы, КЗ, хиты), источником истины не является.
- **character_content_ref** — какие элементы контента и каких версий использовала ревизия, плюс снимок их механики. Благодаря этому персонаж продолжает считаться, даже если источник отключили или удалили.
- **character_state** — всё, что меняется за игровой сессией: текущие и временные хиты, потраченные ячейки и кости хитов, состояния, истощение, подготовленные заклинания, монеты. Эти изменения не создают ревизий.
- **inventory_item** — предметы: ссылка на библиотеку или свой предмет, количество, слот, настройка, магический бонус, заряды, контейнер.

### Кампании

- **campaign** — название, описание, мастер, режим (кампания или ваншот), редакция, статус, текущий уровень, настройки (разрешённые пакеты, вариантные правила, смешивание редакций).
- **player**, **campaign_player** — игроки и их роль в кампании.
- **adventure_log** — история приключений по сессиям.
- **note** — заметки к кампании или персонажу.

## 4. Rules Engine

### Модель персонажа

```ts
CharacterBuild {
  edition: '2014' | '2024'
  options: { abilityMethod, hpMethod, allowFeats, allowMulticlass, allowCrossEdition, variantRules }
  baseAbilities, speciesUid, backgroundUid, originChoices
  levels: LevelEntry[]   // [0] = 1-й уровень персонажа
}
LevelEntry { characterLevel, classUid, classLevel, hpRoll?, choices: ChoiceResolution[] }
```

Персонаж 15-го уровня — это 15 записей в `levels`. Повышение уровня добавляет запись. Отмена повышения переводит указатель на предыдущую ревизию. Один и тот же код считает все три случая.

### Конвейер расчёта

`compute(build, contentResolver, ruleset) → { sheet, pending, issues, usedContent }`

1. **Сбор.** Проход по уровням 1…N: какие особенности даёт вид, предыстория, каждый уровень каждого класса, подкласс, черты.
2. **Выборы.** Каждая особенность может объявить выбор («2 навыка из списка», «стиль боя», «черта или +2 к характеристике»). Ответ ищется в журнале по стабильному `choiceId`. Нет ответа — выбор попадает в `pending`, и мастер покажет его пользователю.
3. **Эффекты.** Особенности, экипировка и настроенные магические предметы дают эффекты на декларативном языке (список типов — в `src/content/schema.ts`): бонус к характеристике, владение, формула базового КЗ, скорость, сопротивление, выдача заклинания, ресурс с перезарядкой и т. д.
4. **Вычисление по фазам** в фиксированном порядке: характеристики → модификаторы → бонус мастерства → владения → КЗ → хиты → скорость → спасброски и навыки → пассивная внимательность → заклинательство и ячейки → атаки.
5. **Проверка.** Требования мультикласса, предпосылки черт, лимиты (настройка не больше 3 предметов, характеристика не выше 20 без особых эффектов), допустимость контента для редакции.

Каждое число на листе — объект `Stat` со списком слагаемых. На экране можно нажать на КЗ и увидеть: «Защита без доспехов: 10 + ЛВК 3 + ТЕЛ 2 = 15; Защита без доспехов монаха (10 + ЛВК + МДР = 14) — не применена, взято лучшее».

### Правила сложения

- Бонусы складываются.
- Эффекты с одинаковым `stackKey` не складываются, берётся лучший. Так работают альтернативные формулы КЗ (варвар и монах), «Дополнительная атака» от разных классов, одноимённые эффекты.
- `ability.set` (вроде пояса силы великана) применяется, только если даёт больше текущего значения.

### Формулы

Формулы в пакетах — строки вида `10 + dex.mod + con.mod` или `max(1, cha.mod)`. Их разбирает собственный маленький парсер в AST: числа, `+ - * /`, `min max floor ceil`, разрешённые имена (`str.mod`, `prof`, `level.total`, `level.class.<id>`). Никакого `eval`. Формула с неизвестным именем не пройдёт импорт.

### Редакции

Всё, что различается в правилах, а не в контенте, живёт в `core/editions/2014` и `core/editions/2024`, реализующих интерфейс `RuleSet`:

| Правило | 2014 | 2024 |
|---|---|---|
| Бонусы к характеристикам при создании | от вида | от предыстории: +2/+1 или +1/+1/+1 среди трёх указанных |
| Черта происхождения | нет | от предыстории |
| Черты | опциональное правило, вместо УХ | категории (происхождения, общие, стиль боя, эпический дар), УХ оформлено как черта |
| Уровень подкласса | данные класса (1, 2 или 3) | данные класса (у всех 3) |
| Мультикласс: уровень заклинателя | полузаклинатели — половина уровня с округлением вниз | половина с округлением вверх (сверить с текстом SRD 5.2.1 тестом) |
| Мастерство оружия | нет | есть |
| Истощение | 6 ступеней с эффектами | −2 к проверкам d20 за ступень |

Уровни УХ, кости хитов, таблицы ячеек и подготовленных заклинаний — это данные класса, а не код. Смешивание редакций возможно только при `allowCrossEdition = true`; такой элемент получает предупреждение на листе.

### Level Engine

- `simulate(build, level)` — состояние на любом уровне. Нужно, чтобы требования мультикласса и предпосылки черт проверялись по характеристикам на момент взятия уровня.
- `previewLevelUp(build, classUid)` — черновик следующего уровня с новыми выборами.
- `diff(sheetBefore, sheetAfter)` — что изменилось: хиты, ячейки, новые способности, атаки.
- Подтверждение создаёт ревизию `level-up`. Повышение сразу на несколько уровней — несколько записей, одна ревизия.
- Отмена последнего повышения — указатель на родителя; сама ревизия не удаляется, поэтому её можно вернуть.
- Восстановление старой версии — новая ревизия `restore` с копией старого журнала. История не теряется никогда.
- Правка решения в прошлом (сменить черту 4-го уровня у персонажа 10-го) пересчитывает всё заново и показывает, что сломалось ниже по цепочке.

### Multiclass Engine

- Требования характеристик и для текущего класса, и для нового — по данным классов, правило проверки — в `RuleSet`.
- Первый класс даёт полные стартовые владения и спасброски; следующие — урезанный набор `multiclass.proficiencies`.
- Бонус мастерства — от общего уровня.
- Ячейки: общая таблица по уровню заклинателя из `multiclassCasterLevel`; магия договора считается отдельно. Подготовка и известные заклинания — по уровню в каждом классе отдельно.
- Дополнительная атака и защита без доспехов не складываются через `stackKey`.

### Spell Engine

- Фильтры по классу, кругу, школе, дистанции, компонентам, длительности, концентрации и ритуалу идут SQL-запросами по индексированным колонкам, поиск по тексту — через FTS5.
- Лимиты подготовленных, известных заклинаний и заговоров — из таблиц или формул класса.
- Заклинания от домена, клятвы и круга выдаются эффектом `spell.grant` с `alwaysPrepared` и не занимают лимит.
- Описание показывается только если `allowed_use.displayText = true`. Иначе — название, параметры и ссылка на страницу источника.

### Inventory Engine

- КЗ от доспеха и щита, требование Силы, помеха Скрытности.
- Атаки оружием: характеристика (Сила, Ловкость для фехтовального и дальнобойного), бонус мастерства при владении, магический бонус, урон, универсальное оружие.
- Настройка — не больше 3 предметов, с проверкой требований.
- Вес и грузоподъёмность по правилам редакции, вариантная нагрузка 2014 — переключатель.
- Монеты хранятся по номиналам, общая сумма считается в медных.

## 5. Контент-пакеты и версионирование

### Пакет

JSON-файл с манифестом и элементами (схема — `src/content/schema.ts`):

```json
{
  "formatVersion": 1,
  "id": "srd-5-2-1",
  "version": "1.0.0",
  "edition": "2024",
  "namespace": "srd521",
  "origin": "builtin",
  "source": { "title": "System Reference Document 5.2.1", "license": { "code": "CC-BY-4.0" }, "allowedUse": { ... } },
  "items": [ { "id": "srd521:class/wizard", "type": "class", "mechanics": { ... }, "text": { ... } } ]
}
```

Встроенные пакеты: `srd-5-1` (2014, английский), `srd-5-2-1` (2024, английский) и их русские переводы `srd-5-1-ru`, `srd-5-2-1-ru`. Всё остальное подключает пользователь.

### Идентификаторы

`namespace:type/slug`, например `srd521:spell/fireball`. ID не меняется между версиями пакета. Версия элемента — это пара «версия пакета + хэш механики». Правка опечатки в описании не меняет хэш и не трогает персонажей.

### Что происходит при обновлении пакета

1. Новая версия ставится рядом со старой.
2. Сравниваются хэши: какие элементы изменили механику.
3. Пользователь видит: «3 персонажа используют изменённые элементы» и для каждого — разницу на листе.
4. Он выбирает: перевести персонажа на новую версию (ревизия `content-migration`) или оставить на старой.
5. Старая версия пакета удаляется автоматически, когда на неё не ссылается ни одна ревизия.

### Отключение и удаление источника

- **Отключение:** элементы пропадают из мастера и поиска. Персонажи считаются по снимкам механики и показывают метку «источник отключён».
- **Удаление:** удаляются тексты и пакет. Снимки механики в персонажах остаются.
- **Удаление со снимками** (например, если права отозваны): у персонажей остаётся только название элемента с пометкой «не установлен». Расчёт идёт без него, а лист показывает, каких чисел не хватает. Подставлять выдуманную замену приложение не будет.

### Лицензии

| Код | Механика | Текст | Показ | Экспорт текста | Делиться |
|---|---|---|---|---|---|
| CC-BY-4.0 (SRD) | да | да | да | да, с атрибуцией | да |
| homebrew-own | да | да | да | да | да |
| permission-granted | по условиям разрешения | | | | |
| user-owned-private | да | да | да | нет | нет |
| unknown | нет | нет | нет | нет | нет — только библиография |

Для пакетов CC-BY атрибуция автоматически попадает в раздел «Источники» приложения и в каждый экспорт. Для перевода SRD в манифесте заполняется `modifications` — что изменено относительно оригинала.

### Импорт

- JSON-пакет: проверка схемы Zod → проверка редакции → проверка ссылок (нет висящих `uid`) → разбор всех формул → поиск дубликатов по `uid` и по названию внутри редакции → отчёт → установка.
- Документы (этап 9): сначала пользователь указывает основание прав. Защищённые и зашифрованные PDF не открываются вообще, приложение объясняет почему. При неизвестных правах сохраняются только библиографические данные.

## 6. Языки: русский и английский

Язык выбирается в настройках, отдельно для интерфейса и для игровых текстов (например, интерфейс на русском, а описания заклинаний в оригинале).

### Интерфейс

- Все строки интерфейса лежат в файлах `locales/ru.json` и `locales/en.json`, в коде их нет. Библиотека — i18next: она умеет русские формы множественного числа (1 ячейка, 2 ячейки, 5 ячеек).
- Игровые термины (характеристики, навыки, состояния, школы магии) берутся из общего словаря, чтобы «Ловкость» везде называлась одинаково.
- Тест проверяет, что в обоих файлах одинаковый набор ключей: забытая строка не попадёт в сборку.

### Контент

- Механика у элемента одна на все языки. Языку принадлежат только название и текст.
- Пакет с контентом написан на одном языке (`language`). Перевод — отдельный пакет `kind: "translation"`, который накладывает названия и тексты на элементы другого пакета. У перевода своя лицензия и свой источник.
- В базе тексты лежат в таблице `content_item_text` по языкам. Если текст на выбранном языке отсутствует, показывается текст на другом языке с пометкой «нет перевода».
- Перевод запоминает хэш исходного текста. Если оригинал обновили, перевод помечается «может быть устаревшим».
- Поиск работает на обоих языках сразу: «огненный шар» и «fireball» найдут одно заклинание.
- Персонаж не зависит от языка: в JSON хранятся только ID, поэтому персонажа, созданного на русском, можно открыть на английском.
- PDF печатается на выбранном языке.

### Объём работы по переводу

Русский перевод SRD — самая трудоёмкая часть наполнения: около 330 заклинаний в каждой редакции, классы, предметы. Предлагаю такой порядок: сначала русские названия всех элементов и полные описания классов и особенностей (без них лист не прочитать), потом описания заклинаний и предметов. Пока перевода нет, показывается оригинал. Пакет с переводом можно обновлять независимо от приложения.

## 7. Экспорт

- **JSON персонажа:** журнал решений, ссылки на контент с версиями, снимки механики. Тексты не включаются — их подставит библиотека получателя.
- **PDF:** описания попадают только из источников с `exportText = true`. Для остальных — название, механика и ссылка на страницу книги. Атрибуция CC-BY добавляется на последнюю страницу.
- **Резервная копия базы:** файл SQLite целиком плюс манифест с контрольной суммой. Восстановление: сначала автоматическая копия текущей базы, потом замена.

## 8. План тестирования

| Уровень | Чем | Что проверяем | Порог |
|---|---|---|---|
| Unit | Vitest | модификаторы, бонус мастерства, парсер формул, предикаты, правила сложения | покрытие `core/` ≥ 95% |
| Свойства | fast-check | модификатор = ⌊(x−10)/2⌋; ячейки мультикласса из одних полных заклинателей = таблица одиночного класса; пересчёт детерминирован; повышение и отмена возвращают исходный лист | 1000 случайных прогонов на свойство |
| Rules Engine | Vitest, эталонные персонажи | лист из JSON сравнивается с эталоном, посчитанным вручную по тексту SRD | 0 расхождений |
| Level Engine | Vitest | создание на N уровне = создание на 1 + (N−1) повышений; правка решения в прошлом; отмена и восстановление | |
| Multiclass | Vitest | требования, владения, ячейки, договор отдельно, отсутствие двойных атак и двойной защиты без доспехов | |
| Языки | Vitest | одинаковые ключи в ru.json и en.json; у каждого элемента встроенных пакетов есть название на обоих языках; запасной язык включается, когда перевода нет | |
| Контент | Vitest | каждый встроенный пакет проходит Zod; нет висящих ссылок; все формулы разбираются; у каждого класса 20 уровней прогрессии | |
| База | Vitest + better-sqlite3 | миграции с нуля и с каждой прошлой версии; репозитории; каскады; персонаж считается после удаления источника | |
| Интеграция | Vitest | импорт пакета → создание персонажа → повышение → экспорт → импорт обратно = тот же лист | |
| E2E | Playwright, WebKit + Chromium, экран iPhone | мастер быстрого и подробного создания, повышение уровня, офлайн-режим PWA | |

### Эталонные сценарии (на базе SRD)

1. 2014 · Холмовой дварф, жрец 1 (домен Жизни), кольчуга и щит — хиты, КЗ, число подготовленных, заклинания домена вне лимита.
2. 2014 · Воин 5 (Чемпион) — Дополнительная атака, критический удар на 19–20.
3. 2014 · Варвар 3 / Монах 2 — защита без доспехов считается один раз, берётся лучшая.
4. 2014 · Волшебник 5 / Жрец 3 — уровень заклинателя 8, общая таблица ячеек.
5. 2014 · Паладин 6 / Колдун 3 — ячейки договора отдельно от общих.
6. 2014 · Паладин 3 / Волшебник 1 и 2024 · то же — разница в округлении уровня заклинателя между редакциями.
7. 2024 · Воин 1 — бонусы характеристик и черта происхождения от предыстории, мастерство оружия.
8. 2024 · Плут 3 — подкласс на 3 уровне, компетентность.
9. Любая редакция · персонаж 20 уровня — полный проход 1→20 совпадает с пошаговым повышением.
10. Распределение по очкам: бюджет 27, диапазон 8–15, отказ при выходе за границы.
11. Персонаж после отключения источника считается по снимку; после удаления со снимками — показывает недостающий контент.
12. Отмена повышения: лист равен листу родительской ревизии побайтно.

Каждый этап разработки закрывается так: сборка → все тесты → исправление → обновление этого документа. Следующий этап не начинается, пока красные тесты предыдущего не исправлены.

## 9. Порядок работы

Этапы — как в ТЗ. Уточнения:

- **Этап 2 (Rules Engine)** начинается с парсера формул и предикатов, потом редакция 2014, потом 2024. К концу этапа — эталонные сценарии 1–8 зелёные на тестовых мини-пакетах.
- **Этап 3 (Content Engine)** — загрузчик, резолвер со снимками, пакеты SRD 5.1 и SRD 5.2.1. Наполнение SRD — самая объёмная часть работы, её можно вести параллельно с этапами 4–6.
- **Этап 4** — первый момент, когда появляется интерфейс. До него всё проверяется тестами.
- После каждого этапа — публикация промежуточной сборки по ссылке, чтобы проверять с iPhone.

## 10. Публикация

Нужен статический хостинг с HTTPS: сервер приложению не нужен, всё работает на устройстве. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Свой сервер Timeweb (где nikahhalal.ru) | Сервер уже оплачен, хостинг в России, свой домен или поддомен, полный контроль | Нужно один раз настроить nginx; другие сайты на сервере не затрагиваются |
| Обычный хостинг в России (Timeweb, Beget, Reg.ru) | Просто, дёшево, быстро открывается в России | Загружать файлы через файловый менеджер хостинга или настроить автозагрузку |
| GitHub Pages | Бесплатно, публикую сам после каждого этапа | Адрес вида `имя.github.io`, из России иногда открывается медленно |
| Vercel, Netlify, Cloudflare Pages | Бесплатно, быстрая публикация | Зарубежные сервисы; из России доступ бывает нестабильным |
| Ссылка на артефакт Claude | Ничего не нужно настраивать | Офлайн-режим и установка на экран «Домой» не гарантированы, нет своего домена |

Варианты можно сочетать. Код живёт в репозитории на GitHub, и после каждого этапа GitHub Actions сам выкладывает сборку на нужный хостинг. Тогда вам не нужно ничего копировать вручную с телефона.

## 11. Решения

- **Название:** A&D. «D&D» и «Dungeons & Dragons» — товарные знаки Wizards of the Coast, поэтому в названии и иконке их нет. В описании пишем «конструктор персонажей для D&D 5e», а в разделе «О приложении» — что продукт неофициальный и с Wizards of the Coast не связан.
- **Публикация:** GitHub Pages. Код лежит в репозитории, GitHub Actions после каждого изменения запускает тесты, собирает и публикует приложение. Если тесты красные, публикации не будет.
- **Языки:** русский и английский, выбор отдельно для интерфейса и для игровых текстов.
- **Стиль:** из ТЗ, отдельно от клуба «Что угодно и драконы».
